## 目标与贯通路径

在同一调查循环中接通“重要判断 → 审查 → 局部修复或保留未决 → 版本化诊断 → 历史记忆”，使 Stage 2 留下的待复核判断获得完整处理路径。

## 实现步骤

1. **接通审查门槛。** 对最终诊断、重要假设排除、证据冲突和依据修订建立 ReviewIssue。Reviewer 使用同一 Executor、预算、工具权限和上下文边界，输出具体判断、依据缺口和可执行修正；原始证据可按权限回取。审查工作在事务外，接受结果时复验版本。
2. **实现局部修复传播。** 分开存储证据支持/反对、判断推导和任务缘由。依据失效先找显式依赖，再按范围发现候选对象；检查独立支持后决定缩小、补查、重新评估或替代。支持组合原因和传播路径，原始观测不随假设排除而删除。
3. **接入停止条件。** 同一目标、范围、问题与依据版本维护稳定问题 ID，默认最多两轮修复。新相关证据或明确新检查才能开启新周期；没有进展或预算不足时保留未决并等待、请求补充或生成部分报告。记录审查采纳情况和修复提交结果。
4. **完成版本化报告。** 将解释、传播路径、支持与反证、重要替代解释、缺口、建议和验证来源写入 Report。生成前检查相关在途任务，提交前复验输入版本；完整诊断和进展报告分别表示。业务恢复单独由观测更新，后续变化形成新报告版本。
5. **接通历史记忆。** 从报告或未完成调查生成不同性质的 MemoryCard，记录来源版本、适用环境、有效和失败路径及未决项。检索优先按项目/环境过滤，再按实体、时间背景与症状排序；跨环境引用标明差异，卡片不能冒充当前证据。
6. **接通失效与可追溯性。** 重要判断进入复核、报告修订或 Case 重新打开时，在同一权威提交中标记报告/卡片待更新；内容异步重建，检索再次检查源版本。记录检索返回版本、进入请求的材料，以及判断—审查—修复—报告的执行关联。
7. **接回产品入口。** CLI 的报告、证据回取和历史查询调用相同服务；人工观察、解释和约束分别转成 Command，调整方向沿用契约变更与取消流程。补充报告、验证状态和记忆使用说明。
